# Project IF — 플레이 세션 및 상태 관리 설계

**문서 상태:** 설계 초안 (v0.1)  
**작성일:** 2026-11-08  
**구현 상태:** JSON 시나리오와 PlayData 연결 완료 / API·Redis·MySQL 연동 예정

## 1. 설계 목적

Project IF는 사용자가 시나리오의 선택지를 고르고, 선택 결과에 따라 점수와 진행 상태가 변경되는 서비스다.

현재 JSON 시나리오를 불러와 PlayData를 통해 단계 진행과 점수 계산, 종료 상태를 처리하는 구조까지 구현했다.

다음으로 실제 웹 환경에서 사용자가 플레이할 때 발생할 수 있는 문제를 고려해야 한다.

- 중복 요청으로 점수가 여러 번 변경되는 문제
- 서로 다른 선택지가 동시에 요청되는 문제
- 브라우저를 실수로 닫은 경우 진행 상태를 복구하는 문제
- 플레이 종료 결과가 중복 저장되는 문제
- DB 저장 과정에서 오류가 발생하는 문제

이를 해결하기 위해 게스트 세션의 저장 위치와 요청 처리 규칙을 분리해 설계한다.

## 2. 데이터 저장 구조

| 구분 | 역할 | 저장 데이터 |
|---|---|---|
| Cookie | 세션 식별 | guestSessionId |
| Redis | 임시 플레이 상태 | 현재 단계, 점수, 선택 이력, 상태 버전 등 |
| MySQL | 최종 결과 보관 | 종료 유형, 최종 점수, 플레이 결과 |

### Cookie

브라우저에는 세션을 식별하기 위한 ID만 저장한다.

점수나 진행 단계는 쿠키에 직접 보관하지 않는다. 서버에서 발급한 세션 ID를 사용하며, HttpOnly·Secure·SameSite 등의 보안 속성을 적용한다.

### Redis

플레이가 진행되는 동안 상태를 임시로 관리한다.

게스트가 브라우저를 닫더라도 Redis 상태가 유효하면 이어서 진행할 수 있도록 한다.

마지막 유효 활동으로부터 1시간 동안 활동이 없으면 세션이 만료되도록 설계한다.

### MySQL

플레이가 포기·실패·클리어 중 하나로 종료되었을 때 결과를 저장한다.

일반적인 선택 과정에서 매번 MySQL에 기록하지 않는다. 비정상 종료나 세션 만료는 플레이 결과 기록 대상에서 제외한다.

## 3. 플레이 상태 모델

Redis에서 관리할 상태의 초안은 다음과 같다.

```json
{
  "sessionId": "guest-session-id",
  "scenarioId": "scenario-001",
  "stageId": "stage-02",
  "score": 70,
  "status": "PLAYING",
  "stateVersion": 2,
  "selectedChoices": [],
  "lastActiveAt": "timestamp"
}
```

각 필드의 역할은 다음과 같다.

- `sessionId`: 하나의 플레이를 식별하는 고유 ID
- `scenarioId`: 진행 중인 시나리오
- `stageId`: 현재 진행 단계
- `score`: 현재 점수
- `status`: 진행 중, 종료 처리 중, 종료 완료 등의 상태
- `stateVersion`: 상태 변경 시 증가하는 버전
- `selectedChoices`: 선택 이력
- `lastActiveAt`: 마지막 유효 활동 시각

실제 Redis 자료구조와 필드 구성은 API 구현 시 확정한다.

## 4. 선택 요청 처리

### 4.1 기본 원칙

하나의 단계에서는 하나의 선택만 정상 반영되어야 한다.

클라이언트가 전송한 점수나 진행 단계를 그대로 신뢰하지 않고, 서버가 현재 상태와 JSON 시나리오를 기준으로 결과를 계산한다.

### 4.2 멱등성 처리

선택 요청에는 다음 정보를 사용한다.

- `requestId`: 개별 요청의 중복 여부를 식별
- `stateVersion`: 요청 당시의 진행 상태를 검증
- `choiceId`: 사용자가 선택한 항목

동일한 requestId와 동일한 요청 내용이 다시 전달되면 점수를 재계산하지 않고 기존 처리 결과를 반환한다.

동일한 requestId에 서로 다른 요청 내용이 사용되었다면 잘못된 재사용으로 판단해 거절한다.

### 4.3 동시 요청 처리

예를 들어 현재 2단계, 70점, 상태 버전 2인 상황에서 서로 다른 두 선택이 동시에 요청될 수 있다.

이때 서버는 상태 버전을 검증한 뒤 하나의 선택만 반영해야 한다.

먼저 정상 처리된 요청이 상태 버전을 3으로 변경했다면, 기존 버전 2를 기준으로 제출된 다른 요청은 거절한다.

Redis에서 상태 검증과 갱신이 하나의 원자적 연산으로 실행되도록 구현한다. 구체적인 구현 방식은 Lua 스크립트 등을 검토한다.

## 5. 플레이 종료 및 결과 저장

종료 유형은 다음 세 가지로 구분한다.

| 종료 유형 | MySQL 기록 |
|---|---|
| 클리어 | 저장 |
| 실패 | 저장 |
| 포기 | 저장 |
| 브라우저 종료·세션 만료 | 저장하지 않음 |

마지막 선택이 종료 조건을 충족하는 경우에도 일반 선택과 동일한 멱등성 및 상태 버전 검증을 거친다.

종료 조건이 확인되면 새로운 선택을 받지 않도록 상태를 전환하고 MySQL 저장 절차를 진행한다.

### 5.1 중복 저장 방지

플레이 세션마다 고유한 ID를 사용한다.

MySQL의 최종 결과 테이블에는 플레이 세션 ID에 UNIQUE 제약조건을 적용한다.

같은 종료 요청이 다시 전달되더라도 동일한 플레이 결과가 중복 저장되지 않아야 한다.

### 5.2 저장 실패 처리

Redis와 MySQL은 하나의 DB 트랜잭션으로 묶이지 않는다.

따라서 종료 상태로 전환한 직후 MySQL 저장에 실패할 수 있다.

이를 고려해 다음 원칙을 적용한다.

- DB 저장이 실패했다고 플레이 결과를 즉시 폐기하지 않는다.
- 재시도 시 같은 세션의 결과가 중복 기록되지 않아야 한다.
- 저장 성공 여부를 확인한 뒤 세션을 정리한다.
- 서버가 저장 중 종료되거나 재시도 전에 Redis 상태가 만료되는 상황에 대한 복구 방식을 별도로 설계한다.

재시도 작업의 지속성과 결과 유실 방지는 구현 단계에서 추가로 확정한다.

## 6. 세션 만료와 이어하기

게스트가 브라우저를 실수로 닫은 경우를 고려해 1시간의 비활동 유예시간을 둔다.

- 정상적인 선택 등 유효 활동이 발생하면 세션 만료 시간을 갱신한다.
- 브라우저를 닫더라도 Redis 상태가 남아 있으면 복구한다.
- 세션이 만료되면 기존 진행 상태는 폐기한다.
- 단순한 탭 전환만으로 플레이를 종료하지 않는다.
- 이미 종료된 플레이의 결과는 Redis 세션 만료와 관계없이 MySQL에 보관한다.

초기 버전에서는 게스트의 임시 플레이를 영구 복구하는 기능까지 제공하지 않는다.

## 7. 구현 후 검증할 항목

| 테스트 상황 | 기대 결과 |
|---|---|
| 정상 선택 요청 | 단계와 점수가 한 번 갱신 |
| 동일 requestId 재요청 | 기존 응답 반환, 추가 변경 없음 |
| 서로 다른 선택 동시 요청 | 한 요청만 정상 반영 |
| 이전 stateVersion 요청 | 상태 변경 없이 거절 |
| 같은 requestId에 다른 선택 전달 | 요청 거절 |
| 마지막 선택 중복 요청 | 종료 처리 한 번만 반영 |
| 종료 결과 중복 INSERT | 결과 레코드 중복 생성 방지 |
| MySQL 저장 실패 | 결과 보존 및 재시도 가능 |
| 브라우저 종료 후 재접속 | 유효 세션이면 이어하기 |
| 1시간 비활동 만료 | 이전 진행 상태 사용 불가 |

테스트는 정상 동작뿐 아니라 중복 요청, 동시 요청, 예외 발생 시 상태가 일관되게 유지되는지를 확인하는 데 중점을 둔다.

## 8. 구현 범위 및 미확정 사항

### 현재 구현한 부분
- JSON 시나리오 로딩
- JSON 선택지와 PlayData 연결
- 점수 계산 및 단계 진행
- 종료 조건 처리와 기본 예외 검증

### 이후 구현할 부분
- REST API 구성
- Redis 기반 게스트 세션
- 선택 요청 멱등성 및 동시성 처리
- MySQL 결과 저장과 중복 방지
- 자동 테스트 및 장애 상황 검증

### 구현 과정에서 확정할 사항
- Redis 상태의 실제 자료구조와 키 구성
- API 요청·응답 형식 및 오류 코드
- 종료 결과 저장 실패 시 복구 및 재처리 방식
- 게스트 식별 정보와 플레이 세션 ID의 관계
- 상태 버전과 중복 요청 처리 기록의 보관 기간

이 문서는 최초 설계 기준이며, 실제 구현 및 테스트 결과에 따라 수정할 수 있다.
