# Project IF 백엔드 기능 동결 및 배포 체크리스트

기준 브랜치는 `wip/f1-timeline-integration`이며, 문서 검토 기준일은 2026-11-27이다. **프론트엔드 연동을 위한 백엔드 기능 동결이 가능하다. 공개 서비스 출시는 배포 전 확인 항목을 통과한 뒤 판단한다.**

## 동결 범위와 완료한 검증

- [x] 백엔드 MVP 주요 기능 구현. 공개 V2 API 6종, JSON 기반 상태·행동·시간 엔진, 시나리오별 이어하기와 포기, 완료 결과·이력 저장, Pending 복구.
- [x] NestJS 빌드 성공. `cd api`에서 `npm.cmd run build`로 재확인.
- [x] 전체 Vitest 테스트 **36개 파일·376/376** 통과. `cd api`에서 `npm.cmd test`로 재확인. 개인 학습용 테스트를 포함한 로컬 집계이며 서비스 테스트는 단위·HTTP·실 Redis/MySQL 통합 등으로 구성된다.
- [x] V1 `/plays` 운영 접근 차단. `LegacyApiGuard`가 루프백 개발과 테스트 환경에서 허용하며 운영은 `404`.
- [x] 개발용 API 접근 제한. `/dev/*`의 등록된 개발 경로는 루프백 개발에서만 허용하며 디버그 상태에는 소유권 검사 적용.
- [x] Redis 연결 설정 분리. 애플리케이션은 `REDIS_URL`을 우선 사용하고 미설정 시 루프백 기본값 사용.
- [x] 게스트 인증·플레이 생명주기. 발급 후 7일 게스트 세션, 조회로 연장하지 않는 1시간 Redis TTL, 게스트·시나리오당 활성 플레이 한 개, 소유권 및 버전 검사.
- [x] 프론트엔드 연동 계약 문서화. [V2 API 계약](API_CONTRACT_V2.md)에 상태별 응답, 재조회, 충돌 및 재시작 흐름을 명시.
- [x] 최초 공개 등록 대상 확인. `office_fire_01`(퇴근하겠습니다)만 공개, 나머지는 비공개.

동결 기준은 여섯 엔드포인트의 바디·응답·상태 코드, 게스트 세션, Redis 버전·TTL 정책과 공개 시나리오 목록이다. 계약이나 배포 차단 결함을 수정해야 할 경우 영향 범위를 문서화하고 관련 HTTP·통합 테스트와 빌드를 다시 확인한다. 콘텐츠 파일 교체는 기존 Redis 플레이의 시나리오 버전에 영향을 주므로 롤아웃에서 별도로 검토한다.

## 배포 전 확인

| 확인 영역 | 공개 전 확인 조건 |
|---|---|
| [ ] 실행 모드 | 실제 프로세스에 `NODE_ENV=production`을 주입한다. `start:prod` 스크립트는 실행 모드를 자체 설정하지 않는다. V1과 개발 경로가 외부에서 `404`인지 확인한다. |
| [ ] 환경변수와 Secret | `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `REDIS_URL`, `PORT`를 점검한다. 배포 설정과 로그에 자격 증명·쿠키가 노출되지 않도록 관리한다. |
| [ ] 데이터 저장소 연결 | API 프로세스에서 Redis/MySQL 연결, 인증, 필요한 권한을 확인한다. Redis/MySQL 포트는 외부에서 직접 접근할 수 없도록 구성한다. |
| [ ] Redis 영속성과 장애 대응 | 영속화·저장 볼륨·메모리 제한 및 축출 정책을 정한다. 재시작 이후 Redis 상태 보존, MySQL 장애 이후 Pending 재처리와 적체 탐지를 검증한다. |
| [ ] MySQL 스키마와 백업 | 빈 DB에 기본 스키마, V2 결과 테이블, 행동 이력 SQL을 순서대로 적용한다. 기존 DB의 이력 컬럼과 데이터 타입을 확인하고 백업·복구를 검증한다. V1 Pending이 남은 DB는 아래 DDL 누락 항목을 확인한다. |
| [ ] HTTPS와 쿠키 | 브라우저에서 HTTPS 발급 응답의 `Secure`, `HttpOnly`, `SameSite=Lax`, 경로와 만료를 확인한다. 이후 API 요청에서 쿠키가 전송되는지 확인한다. |
| [ ] Reverse Proxy | HTTPS 종료, 프론트엔드와 API 경로, 오류 응답, 시간 제한을 검증한다. API 직접 외부 노출과 개발 모드의 프록시 연결을 점검한다. |
| [ ] CORS·CSRF | 동일 출처 구성을 기준으로 API 접근과 쿠키 전송을 검증한다. 출처가 분리되면 허용 origin과 credentials 정책을 정한다. 쿠키 인증 POST에 적용할 CSRF 정책을 정하고 검증한다. 현재 앱 부트스트랩에는 별도 CORS·CSRF 설정이 없다. |
| [ ] Rate Limiting | 시작·행동 등 요청 제한과 응답을 프록시 또는 애플리케이션에서 구성하고 검증한다. |
| [ ] 보안 응답 헤더 | 공개 API와 프론트엔드 응답 헤더를 구성·검증한다. 개발 Playground의 CSP는 해당 HTML 응답에만 적용된다. |
| [ ] 로그 관리 | 요청과 장애를 추적하고 보관 기간·접근 권한·알림을 정한다. 쿠키, 토큰, 비밀번호, 연결 자격 증명을 로그에서 제외한다. |
| [ ] 만료 게스트 세션 정리 | 세션 조회 단계에서 만료를 거절한다. 만료 레코드 정리 주기와 사용자·결과 보관 정책을 정하고 실행을 확인한다. |
| [ ] 콘텐츠와 작업 디렉터리 | 빌드 실행 작업 디렉터리에서 `../data/`와 환경 설정 경로가 해석되는지 검증한다. 시나리오 변경 전 기존 버전 플레이의 유지 또는 자연 만료를 고려한다. |
| [ ] Docker 또는 Docker Compose | API·데이터 파일·런타임 환경의 재현 가능한 구성과 볼륨·스키마 초기화 수단을 준비하고 빈 환경에서 검증한다. |
| [ ] 실제 배포 환경 Smoke Test | HTTPS에서 목록, 신규·기존 게스트, 이어하기·중복·포기, 행동·충돌, 엔딩·이력, 비공개 콘텐츠 접근 제한과 종료 저장을 확인한다. |
| [ ] 사용자 환경 | 모바일·데스크톱 브라우저에서 쿠키, 새로고침, 연속 입력, 충돌·만료·통신 장애와 결과 화면을 확인한다. |

## 확인된 결함과 제약

- **V1 결과 테이블 DDL 누락.** `user_play_log`를 사용하는 V1 결과 저장·복구와 통합 테스트가 존재하지만 저장소 SQL에는 해당 테이블 생성문이 없다. 빈 DB에서 전체 테스트를 그대로 재현하려면 기존 V1 스키마가 필요하다. 운영 V1 HTTP가 닫혀 있어도 부팅 및 주기 작업은 V1 Pending을 스캔하므로, V1 Pending을 이관하는 환경에서는 해당 스키마를 갖춰야 한다.
- **통합 테스트 Redis 주소 불일치 가능성.** 애플리케이션 Redis 주소는 환경변수로 지정할 수 있지만 여러 테스트의 정리 클라이언트는 `redis://127.0.0.1:6379` 고정이다. 통합 테스트 재현 시 애플리케이션과 정리 클라이언트가 같은 격리 Redis를 가리키도록 한다.
- **콘텐츠 버전 교체 영향.** 조회·행동·포기는 현재 JSON을 다시 읽고 View 생성 시 플레이에 저장된 시나리오 버전과 비교한다. 다르면 기존 플레이에서 `500`이 발생할 수 있다. 버전별 콘텐츠 보관·조회 기능은 없다.
- **종료 응답과 DB 저장 사이의 장애.** Redis CAS가 성공한 뒤 MySQL 저장이 실패하면 API가 `500`을 반환해도 플레이는 종료 상태다. 프론트엔드는 플레이를 재조회하고, 운영 환경은 Pending 보존과 재처리를 확인한다.
- **인증 발급 전 중복 요청.** 같은 게스트·시나리오의 중복은 차단하지만, 첫 쿠키가 발급되기 전 동시 시작은 다른 게스트를 만들 수 있다. 프론트엔드에서 시작 버튼의 요청 중 상태를 처리한다.

위 사항의 소스·스키마 변경은 이번 문서 동결 범위에 포함되지 않는다.
